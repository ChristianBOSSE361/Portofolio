## Technical Architecture & Tech Stack

### 1. Frontend
- **HTML5 & Vanilla CSS3**: Custom dark-mode design system with glassmorphism, responsive grids, smooth transitions, and typography.
- **Vanilla JavaScript**: Handles user interactions, API calls to the FastAPI backend, and dynamic chat rendering.
- **Marked.js**: Markdown parser for rendering formatted chatbot responses (bold text, bullet points, code snippets).

### 2. Backend API
- **FastAPI (Python)**: Lightweight, high-performance REST API handling CORS and chat endpoints (`/api/chat`).
- **Deployment**: Hosted on Render.

### 3. RAG Pipeline & AI Components
- **Embedding Model**: `sentence-transformers/all-MiniLM-L6-v2` via Hugging Face Endpoint API (`HuggingFaceEndpointEmbeddings`) with normalized embeddings.
- **Vector Database**: **ChromaDB** (`portofolio_collection`), storing document chunks generated by `RecursiveCharacterTextSplitter` (chunk size: 1000 characters, overlap: 200 characters).
- **LLM Inference**: **Groq API** running `qwen/qwen3.8-27b` (or models such as `llama-3.3-70b-versatile` / `openai/gpt-oss-120b`) with temperature `0.2` for deterministic, precise answers.
- **Orchestration**: Built with **LangChain Core** (`RunnablePassthrough`, `ChatPromptTemplate`, `StrOutputParser`).

---

## Why These Technical Choices Were Made (Design Decisions)
- **Why Groq?**: Extremely low latency inference for real-time chat user experience, providing access to powerful open-weights LLMs like Qwen 2.5/3 and Llama 3.3.
- **Why ChromaDB?**: Lightweight, fast in-memory and persistent vector storage with simple Python integration.
- **Why MMR (Maximum Marginal Relevance)?**: Standard similarity search can return redundant chunks from the same document section. MMR ensures a mix of highly relevant and diverse context fragments.
- **Why Sentence-Transformers (MiniLM-L6-v2)?**: Compact, fast 384-dimensional embedding model with strong semantic matching performance for French and English profile documents.

## Technical Challenges & Solutions
1. **Handling CORS between GitHub Pages and Render**: Configured FastAPI `CORSMiddleware` to strictly allow requests originating from `https://christianbosse361.github.io`.
2. **Formatting LLM Output**: Standard raw text lost line breaks and markdown syntax. Resolved by integrating `marked.js` on the client side and setting `white-space: pre-wrap` for chat bubbles.
3. **Preventing Hallucinations**: Prompt-engineered Onyx with strict instruction rules: only rely on provided context, state gracefully when information is missing, and provide Christian's contact details (`christianbosse123@gmail.com`).

## Frequently Asked / Pertinent Questions (Q&A)

### Q1: What makes this portfolio unique compared to standard portfolio websites?
> **Answer**: Beyond static text, it features an active, embedded AI assistant (Onyx) powered by RAG that allows recruiters and visitors to ask specific questions about Christian's experience, technical stack, or project details in natural language.

### Q2: How does the AI Assistant (Onyx) ensure accurate answers without inventing facts?
> **Answer**: Onyx uses Retrieval-Augmented Generation (RAG). Before generating a response, the system searches ChromaDB vector store for relevant excerpts from Christian's CV and project documentation. The LLM is strictly constrained by prompt engineering to answer ONLY based on these retrieved fragments.

### Q3: How is data ingested and updated in the chatbot's knowledge base?
> **Answer**: Content is written in structured Markdown files (like `about.md`, `experiences.md`, `competences.md`, and project `.md` files) alongside the PDF CV. Running the `ingest.py` script automatically parses, splits, embeds, and updates the ChromaDB vector database.
